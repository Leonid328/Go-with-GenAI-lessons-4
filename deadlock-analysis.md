# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	ch := make(chan int) // небуферизований канал

	wg.Add(1)
	go func() {
		// симуляція важкої роботи
		ch <- 42
		wg.Done()
	}()

	wg.Wait()
	fmt.Println(<-ch)
}
```

## Мій промпт до ШІ

### Мій промпт

Поясни deadlock в цьому Go коді. Не переписуй одразу, спочатку розкажи
по кроках як переплітаються горутини (interleaving).

Код:

```go
var wg sync.WaitGroup
ch := make(chan int) // unbuffered

wg.Add(1)
go func() {
    ch <- 42
    wg.Done()
}()

wg.Wait()
fmt.Println(<-ch)
```

Мені треба:
1. хто на чому блокується (main і горутина)
2. чому `wg.Wait()` перед `<-ch` зависає на небуферизованому каналі
3. яка саме послідовність подій веде до циклічного очікування

Код не виправляй, поки не поясниш зависання.

## Пояснення від ШІ

### Відповідь ШІ

Main робить `wg.Add(1)` і стартує горутину. Горутина одразу йде на
`ch <- 42`. Канал небуферизований, тому send чекає, поки хтось зробить
receive. `wg.Done()` ще не викликано, бо воно стоїть після send.

Main тим часом викликає `wg.Wait()` і чекає Done. Receive `<-ch` ще
не почався. Виходить цикл: горутина чекає читача, main чекає Done,
а Done буде тільки після send. Ніхто не рухається далі.

Якщо б main спочатку прочитав з каналу, send пройшов би, потім Done,
і Wait не зависав би. Або взагалі прибрати WaitGroup - для одного
числа він тут зайвий.

## Мінімальне виправлення

У `deadlock/fixed.go` прибрав WaitGroup. Горутина тільки шле 42 в
канал, а `Run` одразу робить `return <-ch`. Send і receive зустрічаються,
дедлоку немає. Wait перед читанням більше немає.
